# OMNISYS.ui — UI Architecture

**Deliverable §14F.** Cross-platform UI designed from first principles for
OmniScript.

Module README: [`../omnisys/ui/README.md`](../omnisys/ui/README.md).

---

## 1. Design Intent

Study SwiftUI, WPF, Qt, and modern web UI (spec §17.6.2) and extract the
*principles*, not the APIs: declarative composition, reactive state, retained
model with immediate rendering, accessibility as a first-class citizen, layout
engines, animation. The result is a **semantic UI model** that maps onto
Windows, Linux, macOS, browser, and mobile targets — not an "OmniSwiftUI".

## 2. Architecture Layers

```
Semantic UI model (declarative element tree + state)
        │
        ▼
  Renderer / reconciler (diff → minimal updates)
        │
        ▼
  Platform backends: browser DOM · native window · mobile
```

- The **semantic model** is the portable, spec-defined part.
- The **renderer** maps semantic elements to the target's native widgets.
- **State** is reactive: mutations re-render, batched at block boundaries
  (spec §9.4a live-link batching).

## 3. API Shape

```omni
import OMNISYS.ui

element("div", {class: "card"}, [text("Hello")])   # build
row([button("Go", on_click), text("{count}")])     # compose
render(root)                                        # mount
state(value)                                        # reactive state
```

Element values are ordinary typed values (`Element`, `State`), built by pure
functions and composed declaratively. `bind` wires an element attribute to a
state value; `state_set` triggers a batched re-render.

## 4. Live Links

The `UI:` block (`{expression}` slots, `click="fn"`) and `OMNISYS.ui` share
the same reactive model: one state store, one batching rule, one update point
per top-level block. See OMNI_SPEC.md §9.

## 5. Capabilities

- `uses screen` — rendering to a display
- `uses input` — user input events

Both are declared explicitly; a pure computation never renders.
